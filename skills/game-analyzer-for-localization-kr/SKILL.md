# Game Analyzer for Localization KR

## 목적

대상 게임에서 다음 네 항목을 먼저 판별하고, 안전 게이트를 통과한 후보 중 실행 가능한 한국어 패치 제작 방식 하나를 결정한다. 필수 안전 조건을 확인할 수 없으면 방식을 억지로 선택하지 말고 `권장 방식: 보류`로 판정한다.

1. 게임을 이루는 바탕
2. 언어 옵션 추가 가능 여부
3. 폰트 시스템
4. 언어 데이터의 구조 및 분량

분석 결과와 네 항목의 한글화 작업 난이도, 분석 대상 게임의 특이점 2~3개를 작업자가 곧바로 이어받을 수 있는 `KOREAN_LOCALIZATION_PLAN.md`로 저장한다. 이 단계에서는 게임 파일, 세이브, 설정, 실행 파일을 수정하지 않는다.

## 단발성 사용과 후속 작업 인계

이 스킬은 대상 게임·빌드의 최초 사전분석부터 `KOREAN_LOCALIZATION_PLAN.md` 작성과 최종 보고까지만 사용한다.

- 시작할 때 대화 기록과 분석 루트에서 동일 대상·빌드의 완료된 계획서가 있는지 확인한다.
- 완료된 분석이나 계획서가 있으면 이 스킬의 적용을 즉시 끝내고 파일 목록 수집, 재분석, 계획서 갱신을 반복하지 않는다.
- 이후 번역, 용어집·문체 가이드 작성, 폰트·아틀라스 제작, 패치 코드 구현, 추출·재패킹, 실행 검증, LQA, 설치·원복·배포에는 이 스킬을 재사용하지 않는다. 기존 계획서를 후속 작업의 인계 기준으로 사용하고 해당 작업에 맞는 일반 절차나 별도 스킬을 선택한다.
- 사용자가 새 분석 또는 재분석을 명시적으로 요청하고 대상 경로·빌드가 바뀌었거나 기존 결론을 무효화할 새 근거가 있을 때만 별도의 사전분석으로 다시 사용할 수 있다. 단순한 후속 작업 요청은 재사용 근거가 아니다.
- 최종 응답에 이 스킬의 사용이 종료되었으며 다음 작업부터 재사용하지 않는다고 명시한다.

## 판정 근거 수준

주요 판정마다 다음 수준 하나와 신뢰도 `높음/보통/낮음`을 붙인다.

- `관찰`: 파일, 메타데이터, 설정 또는 객체에서 직접 확인했다.
- `정적 추론`: 로더·코드·구조를 근거로 예상했지만 게임에서 실행하지 않았다.
- `실행 검증`: 격리된 복사본에서 실제 동작을 확인했다. 사전 분석 단계에서는 사용자가 별도로 허용하고 실행한 결과가 있을 때만 사용한다.

정적 조사만 수행했다면 `직접 추가 가능` 같은 판정에도 `정적 추론`을 붙이고, 실행 검증이 끝난 것처럼 표현하지 않는다. 서로 다른 근거가 충돌하면 신뢰도를 낮추고 충돌 내용을 남긴다.

## 안전 게이트와 중단 조건

가중치 비교보다 먼저 다음을 확인한다.

- 대상 스토어·플랫폼, 게임 버전 또는 빌드 ID, 실행 파일 해시, OS·아키텍처, 지역·DLC 구성을 식별한다.
- 안티치트, 상시 온라인 무결성 검사, 보호 프로세스, 코드 서명, 암호화·서명된 언어 팩 또는 아카이브, 런타임 해시 검사를 찾는다.
- 폰트와 도구의 수정·재배포 조건을 확인할 근거가 있는지 기록한다.
- 원본 백업, 버전 일치 확인, 격리 복사본, 원복 경로가 가능한지 확인한다.

활성 안티치트·온라인 무결성·보호 프로세스를 우회하거나 비활성화해야 하는 방식은 권장하지 않는다. 공식 모드 경로나 명시적 안전 근거가 없으면 `중단 조건`으로 기록한다. 서명·암호화·라이선스·원복 문제를 해결할 근거가 없으면 관련 후보를 탈락시키고, 모든 후보가 막히면 `권장 방식: 보류`로 쓴다.

## 비용 제한 원칙

다음 원칙을 모든 조사보다 우선한다.

- `rg`와 파일 메타데이터를 먼저 사용한다. 파일 전체를 모델 문맥으로 읽지 않는다.
- 루트 및 1~2단계 하위 폴더부터 조사한다. 근거가 없을 때만 범위를 넓힌다.
- 엔진은 서로 독립적인 서명 두 개가 일치하면 판별을 중단한다.
- 바이너리 검색은 일치 파일명과 최대 몇 줄의 주변 문맥만 출력한다. 큰 DLL의 문자열 전체를 덤프하지 않는다.
- 에셋 컨테이너는 목록이나 헤더만 본다. 엔진 판별을 위해 객체 구조, 텍스처, 메시를 전수 추출하지 않는다.
- 메인 UI, 대화·자막, HUD·월드 UI에서 서로 다른 폰트 경로가 있는지 먼저 구분하고 각 경로의 대표 파일 또는 객체 하나만 확인한다.
- 문자열 분량은 언어 데이터 후보만 계수한다. 게임플레이 수치와 셰이더는 제외하되 이미지 내 문자·지도 라벨·영상 자막·음성·사용자 입력은 범위표에 `포함/제외/미확인`으로 남긴다.
- 전체 어셈블리를 디컴파일하지 않는다. 먼저 타입·문자열 검색을 하고 필요한 클래스나 메서드만 연다.
- 로컬 서명으로 충분하면 인터넷 검색을 생략한다. 불명확할 때만 실행 파일명, 개발사, 고유 파일명을 조합한 검색 1~2회로 확인한다.
- 원본 파일의 정확한 형식이나 로딩 경로를 확인할 수 없으면 추측을 사실처럼 쓰지 말고 신뢰도와 미확인 항목을 기록한다.

## 조사 순서

### 0. 범위 확정

게임 실행 파일이 있는 디렉터리를 분석 루트로 정한다. 사용자가 지정하지 않았다면 현재 작업공간에서 실행 파일과 대표 데이터 디렉터리를 찾는다.

먼저 다음만 수집한다.

- 최상위 실행 파일, DLL, 대형 데이터 파일의 이름과 크기
- 1~2단계 하위 디렉터리 이름
- `Managed`, `Data`, `Content`, `Paks`, `StreamingAssets`, `Localization`, `Lang`, `Fonts`처럼 판별력이 높은 경로
- 스토어·플랫폼, 게임 버전 또는 빌드 ID, 실행 파일 해시, OS·아키텍처, 지역·DLC 구성
- 실행 파일 버전 정보와 분석에 사용한 도구 이름·버전이 저비용으로 보이면 그 값

한 번의 파일 목록 출력이 지나치게 길어지면 확장자·깊이·이름 패턴으로 좁힌다.

다음 범위표를 만들고 각 항목을 `포함/제외/미확인`으로 표시한다. 제외한 항목도 누락 위험과 후속 확인 필요 여부를 기록한다.

| 범위 | 예시 |
|---|---|
| 문자열·UI | 메뉴, 대화, 자막, 튜토리얼, 시스템 메시지 |
| 이미지 내 문자 | 로고, 버튼 텍스처, 지도·표지판, 만화 컷 |
| 영상·음성 | 영상 자막, 음성 더빙, 타이밍 제약 |
| 사용자 입력 | 이름 입력, 채팅, 검색, IME 조합 |

### 1. 게임을 이루는 바탕 판별

다음 우선순위로 분류한다.

1. 문서와 도구가 풍부한 범용 상용·공개 게임 엔진
2. 특정 기업이나 계열사가 라이선스 또는 내부 배포하는 엔진
3. 자체 엔진 또는 판별 불가 사용자 정의 런타임

대표 서명을 우선 사용한다.

| 계열 | 저비용 서명 예시 |
|---|---|
| Unity | `*_Data`, `UnityPlayer.dll`, `globalgamemanagers`, `resources.assets`, `Managed/Assembly-CSharp.dll`, `GameAssembly.dll` |
| Unreal | `Engine/Binaries`, `Content/Paks`, `*.pak`, `*.ucas`, `*.utoc`, `*-Win64-Shipping.exe` |
| Godot | `*.pck`, Godot 실행 파일·섹션 문자열 |
| GameMaker | `data.win`, `options.ini` |
| RPG Maker/NW.js | `www/data`, `Game.exe`, `nw.dll`, `*.json` 또는 `*.rvdata2` |
| Ren'Py | `renpy`, `game/*.rpa`, `*.rpyc` |
| XNA/MonoGame | `*.xnb`, 관련 프레임워크 어셈블리 |

표의 한 항목만으로 확정하지 않는다. 폴더 구조와 런타임 파일처럼 독립적인 증거 두 개를 확보한다. 정확한 세부 버전은 쉽게 확인될 때만 기록한다.

범용 엔진 서명이 없으면 실행 파일 메타데이터, 포함 DLL 이름, 패키지 확장자, 공개된 공식 기술 정보 순서로 기업 엔진 여부를 확인한다. 그래도 특정할 수 없으면 `자체/사용자 정의 엔진`으로 분류하고 관찰된 포맷만 기록한다.

이 단계에서 에셋 파일 내부 객체를 깊게 조사하지 않는다.

### 2. 언어 옵션 추가 가능 여부 판별

#### 2.1 지원 언어와 로더 확인

파일명, 언어 목록 설정, 런타임 로더 중 최소 두 곳에서 언어 코드를 확인한다. 각 언어별 파일 수와 영문 대비 크기를 비교하여 누락된 DLC나 보조 테이블을 찾는다.

다음 항목을 필요한 범위에서 확인한다.

- 언어 목록을 파일명·디렉터리·설정에서 동적으로 발견하는지
- 언어 메뉴가 고정 길이 목록이나 하드코딩된 열거형에 묶이는지
- 언어 코드가 저장 설정, 실행 인수, 플랫폼 언어와 어떻게 연결되는지
- 알 수 없는 언어 코드나 누락된 문자열에 안전한 폴백이 있는지
- 언어 팩에 암호화, 서명, 무결성 검사 또는 고정 인덱스가 있는지

#### 2.2 새 한국어 옵션 직접 추가 가능성

한국어를 독립된 새 언어 옵션으로 추가할 수 있으려면 다음 조건을 확인한다.

- 로더가 새 언어 파일이나 디렉터리를 동적으로 발견하거나 설정 한 곳의 추가만으로 등록할 수 있다.
- 언어별 파일 스키마가 같고 별도 암호화·서명 검증이 없다.
- 언어 선택 UI가 새 항목과 표시 이름을 수용한다.
- 폰트가 한글 글리프를 동적으로 제공하거나 교체 가능한 폰트 자산을 사용한다.
- 문자열 키 누락 시 안전한 폴백이 있거나 모든 키를 복제할 수 있다.

#### 2.3 CJK 슬롯 전환 가능성

직접 추가가 어렵다면 `zh`, `zh-CN`, `zh-TW`, `ja`, `jp` 슬롯을 찾는다. 다음 네 항목만 확인한다.

1. 해당 언어의 문자열 데이터가 영문과 같은 범위를 덮는가
2. CJK 전용 폰트 또는 아틀라스가 실제로 선택되는가
3. 언어 코드에 따른 특수 분기, 줄바꿈, 입력 제한이 한국어를 막는가
4. 기존 슬롯 파일을 같은 형식으로 교체해도 로더가 그대로 읽는가

가장 완전하고 특수 분기가 적으며 폰트 교체가 쉬운 슬롯 하나를 기증 언어로 고른다. 단순히 중국어가 있다는 이유만으로 무조건 `zh`를 선택하지 않는다.

결과를 `직접 추가 가능`, `조건부 가능`, `직접 추가 어려움` 중 하나로 분류하고 근거 수준과 신뢰도를 붙인다. 실행하지 않았다면 `직접 추가 가능(정적 추론)`으로 쓴다. CJK 슬롯 전환이 필요하면 기증 언어와 선택 근거를 함께 기록한다.

### 3. 폰트 시스템 판별

메인 UI, 대화·자막, HUD·월드 UI를 구분하고 각 표면에서 다음 순서로 확인한다. 한 표면의 폰트를 확정했다는 이유로 다른 표면 조사를 생략하지 않는다. 각 표면이 특정 계열로 확정되거나 `미확인`으로 기록되면 멈춘다.

#### A. 동적 TTF/OTF 또는 시스템 폰트

- `.ttf`, `.otf`, `.ttc`, `.woff`, `.woff2` 파일을 이름과 경로로 찾는다.
- 설정·UI 데이터에서 해당 파일명이나 폰트 패밀리 참조를 찾는다.
- DirectWrite, GDI, FreeType, SDL_ttf, 엔진의 동적 Font API 사용 흔적을 필요한 범위에서 확인한다.

폰트 파일과 실제 UI 참조가 함께 확인되면 `동적 윤곽선 폰트`로 분류한다. 파일이 있다는 사실만으로 사용 중이라고 단정하지 않는다.

#### B. 아틀라스 기반 폰트

- `*.fnt`, BMFont XML/JSON, 폰트 이름이 붙은 PNG/DDS/TGA, 머티리얼·스프라이트 메타데이터를 찾는다.
- 클래스 또는 타입 이름에서 `tk2dFontData`, `UIFont`, `BitmapFont`, `FontAtlas`, `TMP_FontAsset`, `TextMeshPro` 등을 검색한다.
- 대표 FontData가 대표 텍스처·머티리얼을 참조하는지만 확인한다.

일반 비트맵과 SDF/MSDF를 구분할 수 있으면 기록하되, 사전 분석 단계에서 아틀라스를 재구성하거나 모든 글리프를 추출하지 않는다.

#### C. 사용자 정의 또는 미확인

A와 B가 모두 부정되면 렌더링 DLL, UI 프레임워크, 셰이더·텍스처 이름에서 최소한의 추가 증거를 찾는다. 다음을 결과에 기록한다.

- 런타임 생성인지 사전 생성인지
- 문자표 또는 코드포인트 사전이 있는지
- CJK용 별도 폰트·텍스처·머티리얼이 있는지
- 추가 분석에 필요한 도구 또는 파일

결과는 반드시 `동적 윤곽선`, `아틀라스(비트맵/SDF)`, `사용자 정의/미확인` 중 하나로 분류하고 신뢰도를 붙인다.

#### D. 한국어 폰트 준비도

확인된 각 폰트 경로에서 필요한 범위만 점검한다.

- 번역 원문에 필요한 완성형 한글·자모·호환 자모·문장부호 코드포인트의 포함 또는 동적 생성 가능성
- 폰트 fallback 순서와 CJK 전용 분기
- 동적 아틀라스의 크기·페이지·캐시 제한 또는 정적 아틀라스의 글리프 수용 여유
- 기준선, 행간, 외곽선·머티리얼·셰이더 호환성
- 폰트 파일의 수정·배포 조건을 확인할 수 있는 근거

폰트 파일에 한글 글리프가 있다는 사실만으로 모든 UI 표면에서 사용할 수 있다고 판정하지 않는다.

### 4. 언어 데이터의 구조 및 분량 판별

#### 4.1 후보 찾기

파일명과 디렉터리명을 먼저 검색한다.

```text
lang, language, locale, localization, loc, text, string,
dialog, subtitle, caption, message, translation, i18n,
en, en-US, english, zh, zh-CN, zh-TW, ja, jp, ko
```

후보 형식은 JSON, JSONC, CSV, TSV, XML, YAML, INI, PO, RESX, TXT, 바이너리 문자열 테이블, 엔진 전용 현지화 패키지를 포함한다. DLC·확장팩·모드 디렉터리도 별도 범위로 기록한다.

#### 4.2 구조 확인

대표 후보 파일의 앞부분과 스키마만 확인하여 다음을 기록한다.

- 저장 형식, 문자 인코딩, BOM·엔디언, 줄바꿈 방식, Unicode 정규화(NFC/NFD)
- 키-값, 행-열, 계층형 객체, 바이너리 문자열 테이블 등 레코드 구조
- 언어별 개별 파일, 다국어 열, 언어별 디렉터리, 통합 컨테이너 중 어느 방식인지
- 문자열 식별자의 안정성, 중복 키, 순서 의존성, 체크섬·오프셋 테이블 존재 여부
- 포맷 자리표시자, 이스케이프, 마크업, 복수형·성별·문법 규칙
- 기본 게임, DLC, 튜토리얼, 자동 생성 이름 등 데이터 범위의 분리 방식

원본 파서의 허용 범위를 모르면 파일을 재직렬화하지 않는다. 구조를 확정할 수 없으면 관찰된 특징과 추가 확인이 필요한 로더를 기록한다.

#### 4.3 영문 분량 산정

영문 후보 파일에서 다음을 계산하고 원문 전체는 출력하지 않는다.

- 파일 수와 합계 바이트
- 레코드·키 수 또는 비어 있지 않은 행 수
- 전체·고유 세그먼트 수, 반복률, 영어 단어 수와 문자 수의 대략값
- 같은 코드의 중복, 포맷 자리표시자, 마크업 존재 여부
- 잠긴 토큰을 제외한 번역 가능 분량과 문맥·화자·화면 정보가 없는 레코드 비율
- 기본 게임, DLC, 튜토리얼, 자동 생성 이름 등 범위별 분량

JSON처럼 보여도 주석이나 중복 키가 있을 수 있으므로 파싱 실패 시 즉시 재직렬화하지 않는다. 정규식 기반 레코드 계수나 줄·문자 수로 대략값을 구하고 형식을 `JSON 유사 형식`으로 기록한다.

번역 규모는 다음처럼 함께 요약한다.

- 소규모: 영어 5만 단어 미만
- 중규모: 영어 5만~20만 단어
- 대규모: 영어 20만 단어 이상

단어 수가 부정확한 표의문자 언어나 바이너리 테이블은 파일 크기와 레코드 수를 우선한다.

#### 4.4 언어별 데이터 범위 비교

각 언어별 파일 수, 레코드 수, 크기를 영문과 비교하여 기본 게임·DLC·보조 테이블의 누락 여부를 기록한다. 이 결과는 2단계의 언어 옵션 추가 가능 여부 판단에도 사용하되, 여기서는 데이터 구조와 번역 범위에 집중한다.

#### 4.5 한국어 문자열·레이아웃·입력 호환성

정적 증거가 있는 범위에서 다음을 확인하고, 실행 확인이 필요한 항목은 LQA 테스트로 넘긴다.

- 문자 수와 바이트 수 제한, substring·타자기 효과·고정 버퍼처럼 멀티바이트 또는 조합 문자를 자를 수 있는 처리
- 한국어 줄바꿈, 자동 크기, 말줄임, 클리핑, 버튼·목록의 고정 폭과 텍스트 확장 여유
- `ko`와 `ko-KR` 매핑, locale fallback, 날짜·숫자·정렬의 언어별 분기
- 사용자 입력이 범위에 포함되면 IME 조합, 허용 문자 필터, 이름·채팅 저장 인코딩
- 의사 번역으로 확인할 대표 화면, 해상도·화면 비율, 입력 장치와 플랫폼 조합

번역 인계 준비에는 용어집, 문체 가이드, 화자·화면·문맥, 연결 문자열, 성별·수량 규칙, 번역 금지 토큰 목록이 필요한지 기록한다. 자료가 없으면 예상 산출물과 선행 작업에 포함한다.

## 최소 확대 조사 규칙

위 단계만으로 결론을 낼 수 없을 때 아래 순서대로 한 단계씩 확대한다. 각 단계에서 답이 나오면 즉시 중단한다.

1. 후보 설정·문자열 파일의 앞부분과 스키마만 확인한다.
2. 패키지의 파일 목록 또는 에셋 이름 테이블만 확인한다.
3. 관리형 어셈블리의 타입 목록과 관련 문자열만 검색한다.
4. 언어 선택 또는 폰트 선택 클래스 한 개만 디컴파일한다.
5. 대표 현지화 객체와 대표 폰트 객체 한 개만 읽는다.
6. 로컬 증거가 충돌할 때만 공식 문서나 신뢰할 수 있는 기술 자료를 검색한다.

대용량 패키지 전체 추출, 전체 어셈블리 디컴파일, 모든 이미지 디코딩은 후속 패치 제작 단계로 넘긴다.

## 최적 방법 하나 결정

안전 게이트를 통과한 후보를 내부적으로 비교하고 최종 결과에는 하나만 `권장 방식`으로 지정한다. 모든 후보가 중단 조건에 걸리면 `권장 방식: 보류`로 지정한다.

1. 새 한국어 로케일을 느슨한 언어 파일로 추가
2. 기존 CJK 언어 슬롯의 문자열과 폰트를 한국어로 교체
3. 엔진 아카이브·에셋 컨테이너 안의 언어 및 폰트 자산을 보존적으로 교체
4. 공식 모드 로더 또는 런타임 후킹으로 문자열·폰트를 주입
5. 실행 파일·사용자 정의 리소스 패치

먼저 다음 하드 블로커를 적용한다.

- 활성 안티치트·온라인 무결성·보호 프로세스의 우회가 필요하다.
- 서명·암호화·체크섬을 보존하거나 공식적으로 다시 만들 방법이 없다.
- 사용·수정·배포 권한을 확인할 수 없는 폰트나 도구를 패키지에 포함해야 한다.
- 대상 빌드 식별, 백업, 버전 일치 확인 또는 원복 절차를 마련할 수 없다.

블로커가 없는 후보는 각 기준을 `0~5점`으로 채점하고 가중치를 적용한다. `0`은 불가능·차단, `1`은 고위험, `2`는 부분 가능·중대한 미확인, `3`은 조건부 실현 가능, `4`는 근거가 충분한 저위험, `5`는 실행 검증까지 끝난 단순한 경로다. 실행 검증이 없으면 해당 기준에 5점을 주지 않는다.

| 기준 | 가중치 |
|---|---:|
| 문자열 접근성과 완전성 | 35 |
| 한글 폰트 적용 가능성 | 30 |
| 언어 선택·로딩 호환성 | 20 |
| 설치·원복 안전성 | 10 |
| 재현 가능한 도구 존재 | 5 |

동점이면 수정 범위가 작고 원복이 쉬운 방식을 선택한다. `직접 추가`가 안전하게 작동하면 이를 우선하고, 하드코딩 때문에 어렵지만 정상 CJK 슬롯이 있으면 `CJK 슬롯 교체`를 우선한다. 컨테이너 수정과 런타임 후킹은 느슨한 파일 방식이 불가능할 때만 선택한다.

결론에는 다음을 한 문장으로 명시한다.

```text
권장 방식: [하나의 방식] — [게임 바탕·언어 옵션·폰트·언어 데이터 구조에 근거한 이유]
```

중단 조건이 남으면 다음 형식을 사용한다.

```text
권장 방식: 보류 — [해결되지 않은 안전·권한·검증 블로커]
```

다른 후보는 `제외 이유`로만 짧게 기록하고 대등한 대안처럼 제안하지 않는다.

## Summary 작성 규칙

Summary의 첫 번째 내용 줄에는 `한글화 패치 제작 전체 난이도: x/10`을 쓴다. `x`는 1~10 범위의 정수 또는 소수점 한 자리로 표시하고, 네 항목을 단순 평균하지 말고 가장 어려운 Details 작업, 안전 블로커, 불확실성, 실행 검증 부담을 함께 반영한다. 이어서 주요 네 항목 각각에 예상 난이도와 짧은 이유를 붙인다. 작업 기간·완료일·소요 시간 수치는 계획서와 최종 응답 어디에도 산정하거나 표시하지 않는다.

예상 난이도 셀에는 난이도 단어와 색상원을 분리하지 말고 다음 조합 중 하나를 그대로 쓴다.

- `하 🟢`: 난이도가 낮으며 초록색 원을 정확히 1개 쓴다.
- `중 🟡🟡`: 난이도가 중간이며 노란색 원을 정확히 2개 쓴다.
- `상 🔴🔴🔴`: 난이도가 높으며 빨간색 원을 정확히 3개 쓴다.

원의 개수나 색상을 단어와 반대로 쓰지 않는다. `하`에 원 2~3개, `상`에 원 1개, 초록색 원 3개 같은 다른 조합은 금지한다.

Summary에는 다음 네 항목을 순서대로 모두 포함한다.

1. 게임을 이루는 바탕
2. 언어 옵션 추가 가능 여부
3. 폰트 시스템
4. 언어 데이터의 구조 및 분량

근거가 부족한 항목은 난이도를 낮게 평가하지 말고 불확실성과 실행 검증 부담을 반영해 보수적으로 평가한 뒤 미확인 사항을 명시한다. 네 항목의 개별 난이도를 평균내어 하나의 종합 등급으로 대체하지 않는다.

계획서와 최종 대화 응답에는 같은 Markdown Summary 표를 사용한다. 계획서에서 표를 한 번 완성한 뒤 행 순서와 셀 내용을 바꾸거나 줄이지 말고 대화창에 그대로 복제한다. `이유`는 45자 이내의 한 문장으로 쓰고 전체 경로·긴 빌드 번호·클래스 목록·복수 근거를 넣지 않으며, 자세한 증거는 뒤의 본문과 근거 파일 목록으로 넘긴다. 대화창 Summary를 불릿 목록이나 문장형 요약으로 바꾸지 않는다.

Summary 표 바로 아래에는 `## Details` 문단과 `기술 작업 | 기술 난이도 | 이유` 표를 둔다.
Details 행에는 권장 방식 구현에 실제로 필요한 핵심 기술 작업 3~5개만 적는다. 서로 이어지는 작업은 한 행으로 합치고 일반적인 백업·설치·원복은 게임 고유 위험이 있을 때만 포함하며, 근거 없는 작업은 채우지 않는다.
기술 난이도는 쉬운 작업 `1/10`, 가장 어려운 작업 `10/10` 기준으로 정수 또는 소수점 한 자리의 `x/10` 형식으로 쓴다. `기술 작업`은 24자, `이유`는 45자 이내의 한 문장으로 쓰고 셀 안 줄바꿈·전체 경로·긴 식별자 나열을 금지하며, 자세한 근거는 뒤의 본문으로 넘긴다.
계획서에서 Details 표를 한 번 완성한 뒤 Summary 표와 마찬가지로 제목, 행 순서, 셀 내용을 변경하지 말고 최종 대화 응답의 Summary 바로 아래에 그대로 복제한다.

이어서 분석 대상 게임에서 실제로 확인된 특이점 2~3개를 간단히 쓴다. 특이점은 한글화 방식이나 검증 범위에 영향을 주는 게임 고유의 구조, 예외, 유리한 조건 중에서 고른다. 일반적인 엔진 설명이나 네 항목의 문장을 그대로 반복하지 않는다.

## 계획서 작성

사용자가 경로를 지정하지 않았다면 분석 루트에 `KOREAN_LOCALIZATION_PLAN.md`를 생성한다. 분석 루트가 쓰기 불가능하면 작업공간의 쓰기 가능한 위치에 생성하고 그 경로를 알린다. 채팅 답변만 요청받았거나 쓰기가 허용되지 않으면 같은 내용을 응답에 제공한다.

다음 구조를 사용한다.

경로와 수치는 실제 조사 결과만 쓴다. 계획 단계와 대상 파일은 선택한 권장 방식에 맞춰 구체화한다. 아직 확인하지 않은 파일을 확정적인 수정 대상으로 적지 않는다.

## 최종 응답

계획서 생성 후 사용자에게 다음만 간결하게 보고한다.

- Summary의 첫 내용 줄에 계획서와 동일한 `한글화 패치 제작 전체 난이도: x/10`을 표시한 뒤, 셀 내용까지 완전히 동일한 간결한 Markdown Summary 표를 이어서 표시한다. 표 열은 `주요 정보 | 예상 난이도 | 이유`로 유지하고 불릿 목록으로 변환하지 않는다.
- Summary 바로 아래에 계획서와 셀 내용까지 동일한 `Details` 기술 작업 표. 열은 `기술 작업 | 기술 난이도 | 이유`로 유지한다.
- 분석 대상 게임의 특이점 2~3개
- 선택한 권장 방식 하나 또는 안전 게이트로 인한 `보류`
- 권장 상태와 근거 수준
- 계획서의 클릭 가능한 절대 경로
- 결론을 바꿀 수 있는 미확인 사항이 있으면 최대 세 개
- 이 응답으로 스킬 사용이 종료되며 후속 작업에서는 재사용하지 않는다는 인계 문구

게임 파일은 수정하지 않았음을 명시한다.
